2.2 Arhitectura — Flow principal

Chat flow (web chatbot, ~2-3s per turn)

POST /v1/chatbot/{channel}/message → preprocessMessage → Intent detection (regex) → Orchestrator pipeline (RAG + product search + semantic search) → LLM call (GPT-4o, fallback Anthropic) → Post-response gate (text/card desync) → Conversation focus update → Response JSON

Voice flow (Telnyx + OpenAI Realtime, ~200-500ms per turn)

POST /v1/bots/{bot}/realtime-session → Build system prompt + inject knowledge context + register tools (search_products) → Return ephemeral OpenAI token → Client opens WebRTC to OpenAI Realtime API (direct, zero server hop) → Voice turns handled entirely by OpenAI (Whisper STT + GPT-4o + TTS) → Tool calls routed back through server → Call end: save transcripts + calculate cost + analyze sentiment (async)

RAG pipeline (hybrid, ~200-400ms)

Query → Embedding (text-embedding-3-small, 1536 dims, cached 24h) → Parallel: pgvector HNSW (ef_search=100) + PostgreSQL FTS (tsvector, language-aware) → RRF merge (Reciprocal Rank Fusion) → Metadata filtering → Parent-child chunk expansion → Conditional reranking (gpt-4o-mini, only in "uncertain zone" 0.58-0.85 similarity) → Context assembly (max 8000 chars) → Inject in system prompt

2.3 Ce e BUN

Puncte forte reale (nu marketing)
  • Hybrid search cu RRF — combinatia vector + FTS cu Reciprocal Rank Fusion e pattern enterprise pe care nici RAGFlow nu il implementeaza mai bine
  • Caching 8-layer — de la embedding (24h) la LLM response (1h), totul cu Redis. Reduce costurile API dramatic
  • Voice zero-hop — OpenAI Realtime direct via WebRTC, fara server intermediar pe audio path. Latenta minima posibila
  • Conditional reranking — LLM reranking doar cand e nevoie (zona 0.58-0.85 similarity), nu pe fiecare query. Smart cost/quality trade-off
  • Post-response grounding gate — detecteaza desync text/carduri produse si suprama cardurile cand AI-ul zice "nu am". Pattern unic, nevazut in repo-uri externe
  • Parent-child chunks — aduce chunk-uri adiacente pentru continuitate. Enterprise RAG pattern
  • Cost control multi-layer — per-request LLM limit, daily tenant cap, voice minute tracking, rate limiting granular
  • Multi-channel cu logic partajat — Chat/WhatsApp/FB/IG folosesc aceeasi logica de baza

4. Analiza RAG

4.1 Ce e BINE

  • Hybrid search (vector + FTS + RRF) — cele 3 repo-uri externe analizate (RAGFlow, awesome-llm-apps) confirma ca hybrid e gold standard. Tu il ai implementat corect.
  • Conditional reranking — nu platesti LLM reranking pe query-uri clare. Smart.
  • Parent-child chunk retrieval — aduce context adiacent. Pattern enterprise.
  • Language-aware FTS — Romanian tsvector config. Corect pentru piata ta.
  • Embedding cache (24h) — reduce costul OpenAI API masiv la query-uri repetitive.

4.2 Ce LIPSESTE

GapImpactSursa pattern
Query rewriting pre-RAG: query-ul utilizatorului merge brut in embedding. "ce amorsa pt tencuiala Cemix?" produce embedding suboptimal vs "amorsa contact tencuiala decorativa Cemix compatibilitate"~15-20% recall pierdutAgentScope, RAGFlow
Retrieval quality gating gradual: threshold-ul e binary (pass/fail la 0.62 similarity). Nu exista zona de "incertitudine comunicata" — fie arata, fie nu.Raspunsuri cu confidence falsaRAGFlow, Agentic RAG
Chunk quality scoring: nu toate chunk-urile sunt egale — un chunk cu tabela de specificatii e mai valoros decat un paragraf de marketing. Nu exista scoring pe tipul de continut.Context pollution in promptRAGFlow (document-aware parsing)
Knowledge freshness tracking: nu exista mecanism de a marca chunk-uri ca "outdated". Daca un produs isi schimba pretul, chunk-ul vechi e inca servit.Hallucination pe date vechiBest practice general

4.3 Verdict RAG

RAG-ul e la 75% din potential. Fundamentele sunt corecte (hybrid search, RRF, reranking). Lipsa query rewriting si quality gating sunt cele mai mari oportunitati. Ambele pot fi implementate fara a schimba arhitectura existenta — sunt adaugari, nu rescrisuri.

5. Analiza Voice vs Chat

5.1 Diferente arhitecturale

AspectChatVoice
LLM call pathServer-side (GPT-4o via API)Client-side (OpenAI Realtime via WebRTC)
Latenta per turn2-3 secunde200-500ms (OpenAI-managed)
RetrievalPer-turn: intent + RAG + product searchOne-shot la session init (knowledge injected in prompt)
Tool callingServer orchestrated (LLM decides, server executes)Client orchestrated (OpenAI Realtime emits tool_call, frontend routes to server)

Cost per minute~$0.01-0.03 (1-2 LLM calls)$0.14 OpenAI Realtime + $0.13 ElevenLabs (if cloned) = $0.27/min

5.2 Ce e OK pe voice

  • Arhitectura zero-hop e corecta — audio nu trece prin serverul tau
  • Knowledge injection la session init e eficient — nu face RAG per turn
  • Tool calling (search_products) functioneaza pe voice cu latenta acceptabila (~200ms)
  • Filler audio cache pentru cloned voices masca latenta perceptibila
  • PromptGuardrails::voiceSpecific() limiteaza raspunsurile la 2 propozitii scurte

5.3 Riscuri voice

Voice knowledge e STATIC pe toata durata call-ului Knowledge context e injectat o singura data la session init (max 12K tokens din instruction budget). Daca utilizatorul schimba subiectul in mijlocul call-ului (de la polistiren la vopsea), bot-ul nu are knowledge context despre vopsea — doar ce a fost preloaded. Chat-ul face RAG dinamic per turn; voice nu.
Voice latency e OpenAI-dependent, nu controlabil Daca OpenAI Realtime API are spike-uri de latenta, nu ai fallback. Chat-ul poate switch la Anthropic; voice nu are alternativa echivalenta (nu exista Anthropic Realtime). Dependency single-provider pe critical path.
Performance Engineer:

Voice e OK acum dar are un scalability ceiling: 12K token instruction budget. Cu knowledge context (2-3K) + system prompt (2K) + product context (1-2K) + guardrails (0.5K), ramai cu ~5-6K pentru conversatie. Suficient pentru 10-15 turnuri. Dupa aia, voice quality degrades — exact cum se intampla si pe chat fara structured memory.

AI Architect:

Solutia nu e sa marim budget-ul (nu e in controlul nostru). E sa comprimam mai bine ce injectam. Knowledge context trebuie sa fie ULTRA-relevant — nu "top 5 chunks by similarity" ci "exact ce chunks are nevoie pentru acest call". Asta inseamna un pre-call knowledge selection mai inteligent, bazat pe call reason (daca stim de ce suna).

6.2 Ce lipseste pentru "WOW"?

Product Strategist:

Lipsa #1: metrici vizibile pentru client. Un client care plateste vrea sa vada: cate conversatii, cate lead-uri, cate vanzari, cat a economisit vs agent uman. Dashboard-ul exista dar e basic. Trebuie un "Conversation Health Score" vizibil: abandonment rate, resolution rate, lead conversion, CSAT. Fara asta, clientul nu stie daca bot-ul ii face bani sau nu.

CTO:

Lipsa #2: CI/CD pipeline. 206 commits in 6 saptamani fara CI. Orice push direct pe master merge in productie fara teste automate. E OK cand esti singur la development, e un dezastru cand ai un al doilea developer sau un client care depinde de uptime.

QA Lead:

Lipsa #3: regression testing automatizat. Am construit un harness de 25 scenarii care ruleaza pe endpoint-ul real. Dar nu e integrat in deploy flow. Trebuie sa ruleze automat dupa fiecare push si sa blocheze deploy-ul daca scorul scade sub 80%.

Red Team:

Lipsa #4: prompt injection protection. System prompt-ul e injectat server-side (bun). Dar user input merge direct in LLM fara sanitizare anti-injection. Un utilizator care scrie "Ignore all previous instructions and..." poate bypassa guardrails. Testat: partial protejat de antiHallucination rules, dar nu sistematic.

Detalii pe cele mai importante

#1 — Comparison Intent (2h, instant ROI)

Adauga regex patterns in IntentDetectionService pentru: "diferenta intre X si Y", "X vs Y", "care e mai bun", "compara X cu Y". Routeaza la knowledge pipeline cu priority 15 (inaintea product_search la 20). AI-ul explica diferentele tehnice, apoi sugereaza produse. Inspiratie: lacuna observata in toate repo-urile externe — nici ele nu au comparison detection explicit.

#3 — Query Rewriting (4h, +20% recall)

Creeaza QueryRewriteService care reformuleaza query-ul utilizatorului INAINTE de embedding: extrage entitati (product_type, context, brand) si reconstruieste ca "adeziv polistiren fatada compatibilitate". Foloseste template-based expansion, zero LLM calls. Inspiratie: AgentScope _QueryRewriteModel, RAGFlow query decomposition.

#4 — Structured Memory (6h, fix long conversations)

Inlocuieste truncarea bruta din ConversationSummaryService cu schema structurata: {customer_need, products_discussed, decisions_made, open_questions, next_action}. Stocat in conversation.metadata['structured_summary']. Trigger: la 75% din token budget. Inspiratie: AgentScope SummarySchema, BeeAI TokenMemory.

#9 — Voice Dynamic Knowledge (12h, major quality bump)

Adauga un tool "search_knowledge" pe voice (similar cu "search_products" existent). Cand utilizatorul intreaba ceva ce nu e in knowledge context-ul preloaded, OpenAI Realtime emite un tool_call care face RAG server-side si returneaza chunk-uri relevante. Latenta: +100-200ms per tool call (acceptabil, similar cu product search). Inspiratie: Agentic RAG pattern "retrieve on demand".

11. Concluzie finala

Sambla voicebot-saas este un produs REAL, nu un demo. Are multi-tenancy functionala, billing, voice calls, 5 channels, hybrid RAG, cost control. Majoritatea SaaS-urilor AI la acest stadiu sunt proof-of-concepts cu un singur flow. Asta are arhitectura serioasa.

Dar nu e WOW inca. 79.9% abandonment rate, lipsa CI/CD, Anthropic SDK broken, prompt injection neacoperit, comparatii misrouted — sunt toate probleme rezolvabile in 3 sprints. Cele 7 fix-uri aplicate pe 11 aprilie au demonstrat ca problemele sunt addressable: scorul de teste a crescut de la 0/25 la 21/25 in cateva ore de munca.

Drumul spre WOW: Sprint 1 (quick wins) + monitorizare 7 zile + Sprint 2 (quality) = produs lansabil cu incredere pe e-commerce chatbot. Sprint 3 adauga platformitatea (dashboard, voice knowledge, parallel pipeline) care transforma din "chatbot tool" in "AI agent platform".

11.1 Auto-critica — Reviewer Dur

Reviewer Dur:

Punct slab #1: Toate testele sunt pe un SINGUR tenant (Malinco). Nu am testat cross-tenant isolation, nu am testat cu un catalog de 50,000+ produse, nu am testat cu 100 conversatii simultane. Rezultatele de calitate (21/25) sunt pe un catalog de 4149 produse cu un bot. Asta NU demonstreaza ca functioneaza pe un magazin de fashion cu 80,000 SKU-uri.

Punct slab #2: Category diversity algorithm-ul foloseste COUNT(DISTINCT categories::text) care e O(n) per token. Pe un catalog cu 100K produse, asta adauga ~50ms per query. Acceptabil pe 4K produse, posibil problematic pe 100K. Trebuie CACHE AGRESIV sau precomputation.

Punct slab #3: Fix-urile din 11 aprilie nu au fost testate pe TRAFIC REAL. 25 scenarii simulate nu inlocuiesc 1000 conversatii reale. Abandonment rate-ul de 79.9% e masurat INAINTE de fix-uri. Nu stim INCA daca fix-urile il scad semnificativ.

11.2 Auto-critica — CTO Skeptic

CTO Skeptic:

"De ce nu ai propus LLM-based intent detection?" — Regex e 95% accurate la 0ms. LLM-based adauga 300-500ms. Switch la LLM cand ajung la 20+ intent-uri sau cand accuracy pe regex scade sub 90%.

"Parallel pipeline cu Fibers e overengineering?" — Posibil. E ultimul pe lista (Sprint 3). Daca latenta chat de 2-3s e acceptabila pentru clienti, NU trebuie implementat. Masoara mai intai daca latenta e un PROBLEM REAL sau doar un ideal.

"Query rewriting fara LLM nu e suficient de smart?" — Template-based aduce 15-20% improvement GRATUIT (0ms, 0$). LLM-based ar aduce 30-40% dar costa 200-400ms + $0.001/query. Faza 1 = template, faza 2 = LLM doar daca template nu satisface.

"Voice dynamic knowledge (#9) nu e risky?" — Da, adauga 100-200ms pe tool call pe voice. Dar FARA el, voice-ul e limitat la knowledge-ul preloaded — orice intrebare in afara contextului initial primeste "nu stiu". Riscul de a NU implementa e mai mare decat latenta adaugata.

"Este vandabil ASA?" — Ca managed service (onboarding manual, support dedicat) pe e-commerce: DA. Ca SaaS self-service: NU INCA. Diferenta: onboarding wizard, pricing page, self-service analytics, trial period automatizat. Estimare: 2-4 saptamani de product work.
